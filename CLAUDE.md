# CLAUDE.md

Starglance: Star Citizen ship and crew status, open source (MIT): Windows agent → hub (one per org, Docker) → fleet page; bots use the hub's integration API. The design and its numbered decisions are in [docs/SPEC.md](docs/SPEC.md) (code comments cite its sections, e.g. "spec §4": keep the numbering); new decisions are appended there, so read the decisions list before changing behaviour. Keep the repo generic: nothing about any particular org, server or person (examples use made-up names and `example.org`).

## Hard rules

- Do **not** copy code from `TheBanjolorian/7hills-link`. It has no license, so implement from the documented behavior only.
- Agent local servers bind `127.0.0.1` only. The single exception is *Show on other devices* (`lanview.py`, spec decision 21): opt-in, paired devices only, view only, with one exception: **Mark this moment** (`POST /api/mark`, decision 25), which only adds a mark to this PC's recent buffer. Never add another route there that changes anything. There is no command path from the network to the game, ever.
- Everything is shared by default, but any category a member switches off never leaves the agent.
- Fixtures must be scrubbed of aUEC and player names before they are committed (handle `TestPilot`, others `Wingmate`; `tests/test_fixtures.py` checks). Raw captures go in the gitignored `captures/` folder.
- The repo is public: no real player names, addresses, tokens or server details in code, tests, fixtures or docs. Test members use made-up names (Rook, Ace, Kestrel...).
- Nothing org-specific in code: the hub address comes from the invite link, the org name from hub settings. No bot code here; bots live in their own projects and use `docs/HUB_API.md`.

## Development

- Python 3.12 via `uv` (`uv sync --python 3.12`, `uv run pytest -q`, `uv run ruff check .`, `uv run ruff format .`). CI runs the same on Ubuntu and Windows, type-checks and builds the page, and builds and starts the hub image.
- Agent code lives in `agent/starglance/` (CLI: `uv run python -m starglance --help`). Tools in `tools/`.
- Set `STARGLANCE_HOME` to a scratch folder when experimenting, so the real `%LOCALAPPDATA%\Starglance` state (settings, hub link) isn't touched.
- Never switch telemetry on/off in the maintainer's real `user.cfg` without asking. Read-only commands (`installs`, `status`, `protoset`) are fine.
- Code map:
  - `shared/starglance_shared/models.py`: the wire schema (Python 3.11-safe; CI checks it). `patch.py`: the merge patches (deltas) agent → hub and hub → page.
  - `agent/starglance/normalize.py` + `events.py`: raw frames to snapshots and events. Every behaviour has a fixture test in `tests/agent/test_normalize.py`.
  - `app.py`: the Windows app (starglance.exe with no arguments, or `python -m starglance app` with `uv sync --extra app`): the agent (`__main__.serve`) on a thread, its own window (pywebview on WebView2, `private_mode=False` so the page's storage persists), a pystray tray icon; closing hides to the tray, a second launch POSTs `/api/app/show`. Optional: no title bar (`frameless`: a new window replaces the old; the page's top bars are `.pywebview-drag-region` with `WindowButtons.svelte`), always on top, Start with Windows (HKCU Run value, exe only). The page talks to the app through `lib/appwin.svelte.ts` (`window.pywebview.api` = `app.Api`). Logs in `logs/starglance.log`. The exe is windowed; commands from a terminal attach to it.
  - `runtime.py` + `localserver.py`: the live pipeline and the 127.0.0.1 server. `lanview.py`: *Show on other devices*, the opt-in view-only server on the home network (port 8741): pairing codes, device keys (hashes in `other-devices.json`), Host/Origin checks; it reuses `LocalServer.stream`/`fleet_stream` with `remote=True`, and the page hides PC-only controls when the hello says `remote` (`web/src/lib/remote.svelte.ts`). `control.py` (`AgentControl`): one uplink per fleet that's on (a PC can be in several orgs' fleets: `fleetlink.FleetSettings.fleets`, each with its own token, sharing and on/off; settings and token file from 0.3 convert on load); the cockpit's Settings → Agent tab (`/api/agent/*`: join or link, leave, sharing, the game's telemetry switch) and the hub uplink's lifecycle; the CLI uses the same functions. `/ws/fleet` relays the hub's `/ws/view` (opened with the PC's token via `Uplink.fleet_view`, only while a page shows the fleet; the page may only send `focus`) for the cockpit's fleet view (`components/LocalFleet.svelte`, `#fleet`) and the Wingmates panel.
  - `gamelog.py`: follows Game.log (read-only) for what the stream lacks: location (armistice, jurisdiction, monitored, restricted, server), quantum route/arrival, contracts and objectives, rewards, kills and losses, injuries. `LogState` turns lines into snapshot state (`location`, `missions`, `session`, `vitals.injuries`) and events. Only recognised lines are kept, captures included. Shared under the `location`, `mission` and `combat` categories, on by default (spec decision 10). Line formats and their history: docs/FIELDS.md, "Game.log". Where you are (`location.landing`, `location.body`, decision 26) comes from landing-area, planet-cells and route-start lines, named by `places.py` from the game's own `global.ini` inside the player's `Data.p4k` (read-only, cached per game version in `names/`; never ship game data in this repo). `tools/demo_places.py` gives the demos the two places their recordings were made at.
  - `fleetlink.py` + `uplink.py`: joining (invite link → account + PC token in one call), linking another PC (code confirmed on the page), one-time sign-in links (`open`), the token (Windows Credential Manager, or a file under `STARGLANCE_HOME`), and the outbound WebSocket: hello, full snapshot, then deltas at up to 10 Hz, events immediately, all through `apply_sharing`/`event_shared`.
  - Hub (`hub/starglance_hub/`): `app.py` every route on one port (pages, accounts, agents, admin, `/api/v1` integrations), `auth.py` sessions and the optional Discord sign-in (the org's own app, set on the admin page; spec decision 29) with its hourly role re-check, `db.py` SQLite with numbered migrations (add to `MIGRATIONS`, never edit one; secrets stored as hashes only, except what must be sent on: the org's Discord client secret and members' Discord tokens, which Download everything strips), `fleet.py` live state, roster summaries and the viewer fan-out (each viewer diffs against what it last sent). A hub with no admin logs a one-time setup link. Admins can download the whole database (`/api/admin/export`); a hub run for an org by someone else (`HUB_HOST_NAME`) says "Hosted by" and records an admin's request to close the org as the setting `close_request`, which the host's tools read (decision 28). Tests in `tests/hub/` run a real hub plus a fake Discord. Running one: `deploy/README.md`; the integration API: `docs/HUB_API.md` (keep it in step with `app.py`).
  - `replay.py`: the fake game over gRPC (`ReplayServer`), plus `Recording` (frames, chapters, event index) and `Playhead` (play/pause/seek/step) for `run --replay`, which `runtime.ReplaySource` feeds straight into the pipeline. A jump (seek, step back, loop) resets the pipeline and the page clears; a new chapter resets the pipeline but keeps the event list.
- Develop without the game: `uv run python -m starglance run --replay --open` (timeline with every event at the bottom of the page; `?customize` opens the Customize drawer on load). To exercise the gRPC path instead: `uv run python tools/replay.py` (port 2943) plus `uv run python -m starglance run --game-port 2943`.
- Run the fleet locally: `HUB_DEV_LOGIN=1 uv run python -m starglance_hub` (sign in by name; the first is admin), make an invite (Admin → Invites, or POST `/api/admin/invites`), then per test member with its own `STARGLANCE_HOME`: `starglance link <invite> --name X` and `starglance run --replay --uplink`. Headless Edge screenshots of the fleet page: get a one-time link (`POST /api/agent/login-link` with the member's token; append `?next=/%3Fadmin` to open the admin dialog, `?next=/%23m=<id>` for a member) and screenshot it. In Git Bash set `MSYS_NO_PATHCONV=1`, or arguments starting with `/` become Windows paths.
- Web UI: `web/`, Svelte 5 + Vite + TS, built with absolute paths (`base: "/"`). `main.ts` asks `/api/mode`: the agent says local (`App.svelte`), the hub says fleet (`components/fleet/FleetApp.svelte`: join, sign-in, link, board). `web/src/lib/types.ts` mirrors the Python models, so change both together. The dashboard is panels (`web/src/lib/panels.ts`: registry, presets, layouts) drawn by `Dashboard.svelte`; each panel in `components/panels/` gets one `ctx` (`lib/context.ts`) and adapts to its own width with `@container panel` queries. Preferences (layout, theme, units) live in `lib/prefs.svelte.ts` (localStorage). Themes are per manufacturer (`lib/themes.ts`, notes in docs/THEMES.md): components use only tokens (no literal colours; `--radius`, `--radius-chip`, `--radius-sm` for corners; `.label` for small labels, `.display` for ship names and big numbers), brand details are `[data-deco]` rules at the end of `app.css`, and `?theme=DRAK&scheme=light` previews one without saving. TypeScript is pinned to 6.x because svelte-check doesn't support TS 7 yet. To check layouts without a browser tool, screenshot with headless Edge (`msedge --headless=new --screenshot=... --window-size=W,H --virtual-time-budget=4000 URL`; use 10000+ for pages with a WebSocket); its minimum width is 500 px.
- Docs site and live demos (GitHub Pages, `.github/workflows/pages.yml`; docs/RELEASING.md "Docs site"): the guide is VitePress Markdown in `site/`; keep it true when a feature changes (same pull request). The demos are `web/demo/` (`index.html` the fleet page with a write-up, `cockpit.html` the real `App` on a recording): `tools/demo_fleet.py` and `tools/demo_cockpit.py` write the gitignored data in `web/showcase/` from the fixtures through the real pipeline (and hub roster code), and `npm run build:showcase` in `web/` builds `web/dist-showcase/`; `npm run demo` in `site/` does all of it into `site/public/demo/`. `lib/demo-fleet.svelte.ts` stands in for the hub connection (`Board` takes `source`, `store`, `embedded`), `lib/demo-live.svelte.ts` for the agent's (`App` takes `live` and `demo`; it answers the replay bar itself). `site/scripts/shots.mjs` takes the docs' screenshots and clips: `demo clips` from the demos (made by the workflow, gitignored), `app` from a real agent and test hub in a temp folder (made-up handle and PC name, test addresses shown as fleet.example.org; committed in `site/public/shots/app/`; look at each before committing).
- The real schema is in [docs/FIELDS.md](docs/FIELDS.md). The normalizer must treat every field as optional: LIVE lacks hull/shields/master mode today, and CIG can change it in any patch.
- Brand: the logo (the wings) and the Discord art are in `brand/`, drawn by `brand/brand-export.cjs`; regenerate rather than redraw. The logo is not MIT (`brand/LICENSE`), and it also lives in `web/src/components/Logo.svelte` (theme colours), the favicon in `web/index.html`, `site/public/logo*.svg` and `favicon.svg`, and `draw_icon` in `agent/starglance/app.py` (exe and tray icon): change them together.
- Branches: `main` is protected (ruleset: pull requests only, CI must pass, no force pushes or deletion). Work on a feature branch, push it and open a pull request; never commit to `main` directly. Release tags are cut from `main` after the merge (docs/RELEASING.md).
- Releases: one version in `pyproject.toml`, `starglance` and `starglance_hub`; tag `v<version>` and `.github/workflows/release.yml` builds `starglance.exe` (PyInstaller, `packaging/starglance.spec`), records a build attestation for it (`actions/attest`; releases are unsigned, and the SignPath step stays off until it's configured), pushes `ghcr.io/bradqui/starglance-hub`, and publishes the release with its notes from the version's section of `CHANGELOG.md` (required: the tag fails without one), then posts that section to Discord if the `DISCORD_RELEASE_WEBHOOK` secret is set (docs/RELEASING.md). Write the changelog for players and admins, not developers: what they'll notice, in plain words. The hub's welcome says the current agent version (its own) and refuses agents older than `MIN_AGENT_VERSION`; the agent contacts nothing but the game and its hubs, except that it asks `github.com/bradqui/starglance/releases/latest` for the latest version (start, every 6 h and on Check now, the redirect only; off in Settings → Agent, `updates.json` "check"), and the Windows app downloads an update from this repo's GitHub release when the user clicks Update or switched on automatic updates (`selfupdate.py`: fixed address from the version number, never a URL from a hub; checksum, and the same signer when signed; swaps the exe, restarts with `--updated`). PRIVACY.md and docs/CODE_SIGNING.md say exactly this: keep them true. Releases must keep the asset names `starglance.exe` and `SHA256SUMS.txt`, which updating relies on.
- Problem reports (docs/REPORTS.md, decision 24): `recent.py` keeps the last 30 minutes (capture format, aUEC scrubbed, marks keep 10 minutes for a day), `report.py` builds the zip, `redact.py` cleans every text in it, `hotkey.py` is the optional global mark key. A report goes only where the player sends it: to a fleet's hub (`POST /api/agent/report` with the PC's key; the hub's `reports.py` checks the zip, keeps it 30 days, admins read it under Admin → Reports and members can delete theirs) or saved to Downloads for a pre-filled GitHub issue. The hub never contacts GitHub. Report routes are on the 127.0.0.1 server only; lanview has only `POST /api/mark` (its own Origin required), and paired devices get the marks but not the report settings (`Reports.for_device`). Anything new that goes into a report must pass through `Redactor` and show in the preview; PRIVACY.md says what's kept.
